# Five real-world DevOps interview questions

## 1. When would you choose a Network Load Balancer over an Application Load Balancer, and what did you use here?

**Answer.** An NLB works at Layer 4. It forwards TCP/UDP/TLS flows with very low latency, handles sudden spikes, gives static IPs (one per AZ, Elastic IPs optional) and supports PrivateLink and non-HTTP protocols. An ALB works at Layer 7 and adds host/path/header routing, redirects, authentication and WAF integration. I pick an NLB for non-HTTP protocols, extreme performance, static IPs or PrivateLink, and an ALB for web apps and microservices that need HTTP-aware routing or WAF. In this project the requirement was a TCP listener, so I used an NLB, but I kept an HTTP health check so the load balancer verifies that Nginx really serves content, not just that port 80 is open. The trade-off to mention: because an NLB does not understand HTTP, there is no path routing or WAF, so I would put an ALB in front if the app needed them.

## 2. The NLB target group shows all targets as unhealthy, but you can see Nginx running on the instance. How do you debug it?

**Answer.** Walk the path of the health check. First `aws elbv2 describe-target-health` to read the *reason* (timeout vs response code mismatch). Timeout usually means the health check packet never reaches Nginx: check the instance security group allows port 80 from the right source. In my design client IP preservation is off, so the source is the NLB and the rule references the NLB security group; if someone enabled preservation, the source becomes the client IP and the rule would block the checks. Then check that Nginx listens on the same port as the target group (`ss -tlnp`), that `curl localhost/` returns 200-399, and that the instance is in a subnet of an AZ the NLB has enabled. Finally check the ASG grace period isn't terminating instances before they are ready. Reachability Analyzer helps to confirm a network-level block. A useful detail: when all targets are unhealthy an NLB fails open and sends traffic to all of them.

## 3. Explain how the target tracking policy works. Why scale in more slowly than scale out, and what would you change for a bursty workload?

**Answer.** With target tracking I choose a metric (`ASGAverageCPUUtilization`) and a target (60%). The ASG creates and manages two CloudWatch alarms: AlarmHigh triggers after about 3 one-minute datapoints above the target and scales out proportionally to the overshoot; AlarmLow requires about 15 low datapoints before scaling in one step at a time. Slow scale-in avoids flapping: removing capacity too early, then needing it again, costs more in warm-up time and user-visible errors than keeping an extra instance for a few minutes. Capacity is always bounded by min (2) and max (4). Warm-up settings stop new instances from skewing the average. For a bursty workload I would lower the target (more headroom, for example 40-50%), use scheduled scaling for known peaks, consider predictive scaling, keep a higher minimum, and make the AMI/user data lighter (a pre-baked AMI) so new instances become healthy faster. If CPU is not the bottleneck, I would track a different metric such as request count per target or a custom queue-depth metric.

## 4. What are the single points of failure in this architecture and how would you make it more resilient, and what does that cost?

**Answer.** Serving traffic is highly available: the NLB has a node in two AZs, instances run in two AZs, the ASG replaces failed instances (ELB health checks), and cross-zone balancing evens out the load. The one default single point of failure is the single shared NAT Gateway: if its AZ fails, private instances lose outbound access (package installs, SSM), though existing traffic through the NLB continues to work. I made that a variable (`single_nat_gateway`): `false` creates one NAT Gateway per AZ and routes each private subnet to the NAT in its own AZ, at roughly double the NAT cost. Other improvements: three AZs, a pre-baked AMI (so launch does not depend on `apt` and the internet), VPC endpoints for SSM/S3 to avoid NAT dependency and charges, a higher minimum capacity, multi-region with Route 53 failover for regional outages, and removing the one-region state bucket as a dependency by enabling replication. Cost versus resilience is a business decision, so I documented the trade-off instead of hiding it.

## 5. How do you manage Terraform state safely in a team, and why did you add `ignore_changes = [desired_capacity]` and some explicit `depends_on`?

**Answer.** State is stored remotely in a versioned, encrypted, private S3 bucket with native locking (`use_lockfile`, Terraform 1.10+), so two people cannot apply at the same time and a corrupted state can be rolled back from a previous version. State can contain secrets, so access to the bucket is restricted and the state file is never committed; account-specific bucket settings are passed through `backend.hcl` at `terraform init`. In CI I would run `plan` on pull requests and `apply` only from the main branch using an assumed IAM role. `ignore_changes = [desired_capacity]` is needed because the scaling policy changes the desired capacity at runtime; without it every `terraform apply` would reset the group to the value in code and fight the autoscaler. Terraform builds the dependency graph from references, and I use `depends_on` only where it cannot see the dependency: the ASG must wait for the listener (a target group has to be attached to a load balancer before an ASG can register with it) and for the private NAT routes (otherwise the first instances boot without internet and `apt install nginx` fails), and the NAT Gateway/EIP/NLB need the Internet Gateway attached first.
